# Беклог WISLA Fault Management

Отложенные задачи, которые **не** входят в текущий инкремент. Оркестратор `/build-feature` и агенты смотрят сюда, если пользователь просит «что дальше», «из беклога», «следующую задачу» — не выдумывать scope заново.

Статусы: `ready` — можно брать в `/build-feature`; `blocked` — ждёт зависимостей; `parked` — сознательно позже.

**Идентификаторы.** У каждого пункта стабильный ключ `FM-<n>` (например `FM-1`). Это ключ для воркфлоу, когда нет тикета Jira: ветка `feature/FM-<n>`, первая строка коммита `FM-<n>`, вызов `/build-feature FM-<n>`. Не выдумывать URL Jira для `FM-*`. Если у задачи есть тикет Wellink — использовать ключ Jira (`WISLA-<n>`), а не `FM-<n>`.

**Приоритеты** (отдельно от статуса):

- **Критический** — без этого продукт не работает.
- **Высокий** — без этого продукт нельзя нормально демонстрировать или запускать в пилот.
- **Средний** — существенно улучшает продукт.
- **Низкий** — можно сделать позже.

## FM-5 — Лицензирование: пакеты продуктов, подписка/коробка, attach к wiSLA

| | |
|---|---|
| **Ключ** | `FM-5` |
| **Статус** | `ready` |
| **Приоритет** | `Высокий` |
| **Модули** | коммерция / оферта; при необходимости — контроль лимита продуктов в `fm-module` |
| **Документы** | [`docs/licensing-for-marketers.md`](docs/licensing-for-marketers.md), [`docs/licensing-options.md`](docs/licensing-options.md), [`docs/go-to-market.md`](docs/go-to-market.md) |

**Выбранный путь.** Одна линейка модуля FM, не несколько продуктов. Сборка: **пакеты продуктов** (рост) + **две кассы** (подписка или бессрочно) + **скидка клиентам wiSLA**. Запасной путь «плоский инстанс, всё безлимит» — только если закупка откажется считать продукты; в маркетинге по умолчанию не вести.

Позиция: продаём модуль аварий, не коллектор и не ITOM. Метрика — **продукты на карте здоровья**, не хосты, не NVPS, не источники, не кресла в консоли.

**Продукт в договоре.** Объект на карте здоровья, который смена видит как отдельную услугу (магазин, ДБО, платёжный контур). КЕ, хосты и источники событием лицензии не являются. Несколько систем сбора на одну услугу = один продукт.

**Пакеты (SKU).**

| Код | Клиенту | Состав |
|---|---|---|
| `FM-PILOT` | Пилот | 1 продукт, 90 дней; NFR или зачёт в первый год |
| `FM-5` / `FM-15` / `FM-UL` | FM 5 / 15 / безлимит | Полный модуль, лимит продуктов |
| `FM-WISLA` | Скидка wiSLA | Не другой софт, а цена на тот же пакет при действующем wiSLA |
| `FM-SUP` | Сопровождение | Обязателен на бессрочной; на подписке обычно внутри года |

Путь клиента: пилот → рабочий пакет → если wiSLA, скидка на этот пакет → если коробка, ежегодное сопровождение.

**Касса.** Подписка 12 мес (вход ниже, сопровождение в годе) или бессрочно + `FM-SUP` (~20%/год). Бессрочная ≈ 2–2,5 годовых, чтобы не съесть подписку. Скидка wiSLA 20–35% к пакету, модуль отдельной строкой, не «в нагрузку» бесплатно.

**Коридор цены (не прайс).** Рабочий пакет (ориентир FM-5) — заметно ниже полки, где у зонтичных ITOM живут fault и здоровье услуг (~1,2 млн ₽, Monq Business). Иначе нет клина «купите модуль, не платформу». Точные ₽ утверждает коммерция. В клиентские тексты не ставить «дешевле конкурента на N ₽» до утверждённого прайса.

**Что сделать.**

1. Зафиксировать модель в прайсе и оферте: определение продукта, пакеты, две формы оплаты, attach wiSLA, пилот 90 дней.
2. Вычистить клиентские формулировки по [`docs/licensing-for-marketers.md`](docs/licensing-for-marketers.md) (юристом / маркетингом).
3. По решению коммерции — технический контроль лимита продуктов (не пускать 6-й продукт на FM-5) либо пока учёт только договорной.

**Не делать.** Тариф за хосты / NVPS / агенты / источники / операторов консоли. Прятать FM в дорогую редакцию «Максимум/Business». Бессрочный бесплатный Community. Отдавать софт за $0 и брать только внедрение. Продавать `FM-WISLA` без wiSLA. Продавать только `FM-SUP` без лицензии модуля. Реализовывать license-сервер / аппаратные ключи / онлайн-активацию «как у SAP», пока не решили, нужен ли технический контроль. Запасной плоский инстанс (вариант B) не делать основной полкой.

**Текущее состояние.** ~17 активных тестов в 3 spec-файлах: smoke маршрутов (`routes`), граф здоровья (`health-graph`), CRUD продукта здоровья (`health-product-crud`).

**Цель.** Расширить Playwright-покрытие пользовательских сценариев по [`docs/pages-spec.md`](docs/pages-spec.md), [`docs/demo/`](docs/demo/), [`openspec/specs/`](openspec/specs/). Полная матрица сценариев (~120+ кейсов по областям) — в discovery-чате; реализация по фазам.

**Области покрытия (матрица сценариев):**

- **auth** — вход, сессия, выход, защита маршрутов

**Фазы.**

- **Phase 1 (smoke + demo):** критичный минимум для CI и demo-стенда — маршруты, auth, demo path, базовая консоль.
- **Phase 2 (critical regression):** rules runtime, sources lifecycle, push toasts, admin CRUD, role-based, расширенный health.

**Что сделать.** По матрице сценариев добавить spec-файлы и кейсы в `frontend/tests/e2e/`, подключить прогон в CI, обеспечить стабильность на demo-стенде.

## FM-19 — Фильтр по приоритету при клике на счётчики дашборда

| | |
|---|---|
| **Ключ** | `FM-19` |
| **Статус** | `done` |
| **Приоритет** | `Критический` |
| **Модули** | `frontend/` (Dashboard `/`, консоль `/console`, карты событий) |

**Проблема.** На дашборде отображаются счётчики, сколько событий случилось по приоритетам (Critical / Major / Minor / Warning). По клику, например на Critical, открываются **все** события без фильтра по приоритету. По [`docs/pages-spec.md`](docs/pages-spec.md) счётчики должны вести в `/console` **с соответствующим фильтром** (1 клик).

**Что сделать.** При клике на счётчик приоритета открывать консоль (или карту событий) уже с фильтром по этому приоритету. Рассмотреть перенос самих счётчиков/виджетов с дашборда на карту событий, если там дежурному удобнее смотреть и сразу фильтровать поток.

**Не делать.** Не менять расчёт счётчиков и не расширять дашборд новыми виджетами сверх приоритетов и переноса на карту.

## FM-20 — Плитки продуктов с % здоровья на Dashboard

| | |
