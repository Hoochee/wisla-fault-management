# Беклог WISLA Fault Management

Отложенные задачи, которые **не** входят в текущий инкремент. Оркестратор `/build-feature` и агенты смотрят сюда, если пользователь просит «что дальше», «из беклога», «следующую задачу» — не выдумывать scope заново.

Статусы: `ready` — можно брать в `/build-feature`; `blocked` — ждёт зависимостей; `parked` — сознательно позже.

**Приоритеты** (отдельно от статуса):

- **Критический** — без этого продукт не работает.
- **Высокий** — без этого продукт нельзя нормально демонстрировать или запускать в пилот.
- **Средний** — существенно улучшает продукт.
- **Низкий** — можно сделать позже.

## FM-product-health — выделить Product Health в микросервис

| | |
|---|---|
| **Ключ** | `FM-product-health` (follow-up) |
| **Change (черновик)** | `health-service-extract` |
| **Статус** | `blocked` — сначала стабилизировать формулу/API в текущем change `product-health-graph` |
| **Приоритет** | `Средний` |
| **Модули** | новый deployable (не invent без approval), `backend/fm-module`, `frontend/`, compose |

**Почему отложено.** Health — read-model над событиями и CMDB. В инкременте `product-health-graph` расчёт остаётся bounded context внутри `fm-module` (гексагональные швы, снимки, REST `/api/v1/health/*`). Отдельный сервис сейчас = вторая БД, JWT, рассинхрон снимка при ещё не зафиксированной формуле.

**Когда брать.** После того как на демо Gift Shop прогнаны: веса, snapshot/history, Sankey с сервера, pull `/metrics` через adapter.

**Что сделать.** Скопировать пакет `ru.wisla.fm.health` в новый сервис; таблицы `product_component*`, `product_health_snapshot`, `product_health_history`; подписка на доменные события вместо in-process listener; тот же префикс `/api/v1/health` (прокси в fm-module или прямой DNS). Не ломать SPA.

**Не делать при выделении.** Shared Maven-jar между adapter и health; прямой ingest в health в обход adapter.

## Product Health — RCA, combo, покрытие мониторингом

| | |
|---|---|
| **Ключ** | `FM-product-health` (follow-up) |
| **Статус** | `parked` — не нужно для графа как на скрине Monq Ops Center Health |
| **Приоритет** | `Низкий` |
| **Зависит от** | `product-health-graph` (формула `H = min(h_direct, h_ratio)`, веса) |

Кратко, что это и зачем не в текущем инкременте — см. комментарий в чате discovery / раздел ниже в воркфлоу. Суть:

- **RCA (анализ первопричин)** — обход дерева влияния до листовых сигналов с уроном по веткам. Нам достаточно прямых сигналов на КЕ продукта.
- **Combo** — «k из n должны упасть» (HA). Для Gift Shop не нужно; достаточно weighted + critical.
- **Покрытие мониторингом** — % заполненных слотов порогами. В Monq **не** входит в формулу здоровья.

## Как добавлять пункты

1. Заголовок + ключ (Jira или внутренний id).
2. Статус, приоритет (Критический / Высокий / Средний / Низкий), модули, зависимость от активного change.
3. Почему отложено / критерий «можно брать».
4. Не тащить в текущий `/build-feature`, пока пользователь явно не скажет взять пункт из беклога.
