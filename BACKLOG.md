# Беклог WISLA Fault Management

Отложенные задачи, которые **не** входят в текущий инкремент. Оркестратор `/build-feature` и агенты смотрят сюда, если пользователь просит «что дальше», «из беклога», «следующую задачу» — не выдумывать scope заново.

Статусы: `ready` — можно брать в `/build-feature`; `blocked` — ждёт зависимостей; `parked` — сознательно позже.

**Идентификаторы.** У каждого пункта стабильный ключ `FM-<n>` (например `FM-1`). Это ключ для воркфлоу, когда нет тикета Jira: ветка `feature/FM-<n>`, первая строка коммита `FM-<n>`, вызов `/build-feature FM-<n>`. Не выдумывать URL Jira для `FM-*`. Если у задачи есть тикет Wellink — использовать ключ Jira (`WISLA-<n>`), а не `FM-<n>`.

**Приоритеты** (отдельно от статуса):

- **Критический** — без этого продукт не работает.
- **Высокий** — без этого продукт нельзя нормально демонстрировать или запускать в пилот.
- **Средний** — существенно улучшает продукт.
- **Низкий** — можно сделать позже.

## FM-2 — Выделить Product Health в микросервис

| | |
|---|---|
| **Ключ** | `FM-2` |
| **Change (черновик)** | `health-service-extract` |
| **Статус** | `blocked` — сначала стабилизировать формулу/API в текущем change `product-health-graph` |
| **Приоритет** | `Средний` |
| **Модули** | новый deployable (не invent без approval), `backend/fm-module`, `frontend/`, compose |

**Почему отложено.** Health — read-model над событиями и CMDB. В инкременте `product-health-graph` расчёт остаётся bounded context внутри `fm-module` (гексагональные швы, снимки, REST `/api/v1/health/*`). Отдельный сервис сейчас = вторая БД, JWT, рассинхрон снимка при ещё не зафиксированной формуле.

**Когда брать.** После того как на демо Gift Shop прогнаны: веса, snapshot/history, Sankey с сервера, pull `/metrics` через adapter.

**Что сделать.** Скопировать пакет `ru.wisla.fm.health` в новый сервис; таблицы `product_component*`, `product_health_snapshot`, `product_health_history`; подписка на доменные события вместо in-process listener; тот же префикс `/api/v1/health` (прокси в fm-module или прямой DNS). Не ломать SPA.

**Не делать при выделении.** Shared Maven-jar между adapter и health; прямой ingest в health в обход adapter.

## FM-3 — Product Health: RCA, combo, покрытие мониторингом

| | |
|---|---|
| **Ключ** | `FM-3` |
| **Статус** | `parked` — не нужно для графа как на скрине Monq Ops Center Health |
| **Приоритет** | `Низкий` |
| **Зависит от** | `product-health-graph` (формула `H = min(h_direct, h_ratio)`, веса) |

Кратко, что это и зачем не в текущем инкременте — см. комментарий в чате discovery / раздел ниже в воркфлоу. Суть:

- **RCA (анализ первопричин)** — обход дерева влияния до листовых сигналов с уроном по веткам. Нам достаточно прямых сигналов на КЕ продукта.
- **Combo** — «k из n должны упасть» (HA). Для Gift Shop не нужно; достаточно weighted + critical.
- **Покрытие мониторингом** — % заполненных слотов порогами. В Monq **не** входит в формулу здоровья.

## FM-5 — Лицензирование: пакеты продуктов, подписка/коробка, attach к wiSLA

| | |
|---|---|
| **Ключ** | `FM-5` |
| **Статус** | `ready` |
| **Приоритет** | `Высокий` |
| **Модули** | коммерция / оферта; при необходимости — контроль лимита продуктов в `fm-module` |
| **Документы** | [`docs/licensing-for-marketers.md`](docs/licensing-for-marketers.md), [`docs/licensing-options.md`](docs/licensing-options.md), [`docs/go-to-market.md`](docs/go-to-market.md) |

**Выбранный путь.** Одна линейка модуля FM, не несколько продуктов. Сборка: **пакеты продуктов** (рост) + **две кассы** (подписка или бессрочно) + **скидка клиентам wiSLA**. Запасной путь «плоский инстанс, всё безлимит» — только если закупка откажется считать продукты; в маркетинге по умолчанию не вести.

Позиция: продаём модуль аварий, не коллектор и не ITOM. Метрика — **продукты на карте здоровья**, не хосты, не NVPS, не источники, не кресла в консоли.

**Продукт в договоре.** Объект на карте здоровья, который смена видит как отдельную услугу (магазин, ДБО, платёжный контур). КЕ, хосты и источники событием лицензии не являются. Несколько систем сбора на одну услугу = один продукт.

**Пакеты (SKU).**

| Код | Клиенту | Состав |
|---|---|---|
| `FM-PILOT` | Пилот | 1 продукт, 90 дней; NFR или зачёт в первый год |
| `FM-5` / `FM-15` / `FM-UL` | FM 5 / 15 / безлимит | Полный модуль, лимит продуктов |
| `FM-WISLA` | Скидка wiSLA | Не другой софт, а цена на тот же пакет при действующем wiSLA |
| `FM-SUP` | Сопровождение | Обязателен на бессрочной; на подписке обычно внутри года |

Путь клиента: пилот → рабочий пакет → если wiSLA, скидка на этот пакет → если коробка, ежегодное сопровождение.

**Касса.** Подписка 12 мес (вход ниже, сопровождение в годе) или бессрочно + `FM-SUP` (~20%/год). Бессрочная ≈ 2–2,5 годовых, чтобы не съесть подписку. Скидка wiSLA 20–35% к пакету, модуль отдельной строкой, не «в нагрузку» бесплатно.

**Коридор цены (не прайс).** Рабочий пакет (ориентир FM-5) — заметно ниже полки, где у зонтичных ITOM живут fault и здоровье услуг (~1,2 млн ₽, Monq Business). Иначе нет клина «купите модуль, не платформу». Точные ₽ утверждает коммерция. В клиентские тексты не ставить «дешевле конкурента на N ₽» до утверждённого прайса.

**Что сделать.**

1. Зафиксировать модель в прайсе и оферте: определение продукта, пакеты, две формы оплаты, attach wiSLA, пилот 90 дней.
2. Вычистить клиентские формулировки по [`docs/licensing-for-marketers.md`](docs/licensing-for-marketers.md) (юристом / маркетингом).
3. По решению коммерции — технический контроль лимита продуктов (не пускать 6-й продукт на FM-5) либо пока учёт только договорной.

**Не делать.** Тариф за хосты / NVPS / агенты / источники / операторов консоли. Прятать FM в дорогую редакцию «Максимум/Business». Бессрочный бесплатный Community. Отдавать софт за $0 и брать только внедрение. Продавать `FM-WISLA` без wiSLA. Продавать только `FM-SUP` без лицензии модуля. Реализовывать license-сервер / аппаратные ключи / онлайн-активацию «как у SAP», пока не решили, нужен ли технический контроль. Запасной плоский инстанс (вариант B) не делать основной полкой.

## FM-6 — Расширить покрытие e2e тестами (Playwright)

| | |
|---|---|
| **Ключ** | `FM-6` |
| **Статус** | `ready` |
| **Приоритет** | `Критический` |
| **Модули** | `frontend/tests/e2e/`, CI, demo-стенд |

**Текущее состояние.** ~17 активных тестов в 3 spec-файлах: smoke маршрутов (`routes`), граф здоровья (`health-graph`), CRUD продукта здоровья (`health-product-crud`).

**Цель.** Расширить Playwright-покрытие пользовательских сценариев по [`docs/pages-spec.md`](docs/pages-spec.md), [`docs/demo/`](docs/demo/), [`openspec/specs/`](openspec/specs/). Полная матрица сценариев (~120+ кейсов по областям) — в discovery-чате; реализация по фазам.

**Области покрытия (матрица сценариев):**

- **auth** — вход, сессия, выход, защита маршрутов
- **demo source path (`FM-1`)** — пользовательский путь демо от входа до заведения КЕ на мониторинг
- **console / event card** — консоль событий, карточка события
- **rules runtime** — правила обработки в runtime
- **sources lifecycle** — жизненный цикл источников
- **push toasts** — push-уведомления в UI
- **admin CRUD** — админские операции
- **role-based** — доступ по ролям
- **health** — Product Health (граф, снимки, история)

**Фазы.**

- **Phase 1 (smoke + demo):** критичный минимум для CI и demo-стенда — маршруты, auth, demo path, базовая консоль.
- **Phase 2 (critical regression):** rules runtime, sources lifecycle, push toasts, admin CRUD, role-based, расширенный health.

**Что сделать.** По матрице сценариев добавить spec-файлы и кейсы в `frontend/tests/e2e/`, подключить прогон в CI, обеспечить стабильность на demo-стенде.

## FM-10 — Действия дежурного на аварии (ack, comment, assign, silence)

| | |
|---|---|
| **Ключ** | `FM-10` |
| **Статус** | `ready` |
| **Приоритет** | `Высокий` |
| **Модули** | `backend/fm-module` (`EventActionService`), `frontend/` консоль и карточка |
| **Откуда** | оперцентр Monq; у нас только take (себе) и close |

**Зачем (FM).** Консоль — рабочее место NOC. Сейчас нельзя подтвердить аварию отдельно от take, написать комментарий в UI (API comment уже есть), назначить коллеге, временно скрыть шум.

**Что сделать.** На карточке события и из консоли: **ack** (подтвердить, событие остаётся активным), **comment** (кнопка на существующий API), **assign** на другого пользователя, **silence** на N минут (не показывать в активных, не слать notify, не сбрасывать PROBLEM). Take/close не ломать.

**Не делать.** Матрицы эскалации, смены/on-call, downtime-календарь как модуль, согласование, ITSM, массовые операции на тысячи строк, WebSocket.

## FM-11 — Шторм алертов на продукт

| | |
|---|---|
| **Ключ** | `FM-11` |
| **Статус** | `ready` |
| **Приоритет** | `Средний` |
| **Зависит от** | стабильный `product-health-graph` (`product_ci`) |
| **Модули** | `backend/fm-module` (processing + health), консоль |
| **Откуда** | графа Monq «защита от шторма на весь продукт, не на подсистемы» |

**Зачем (FM).** Dedup схлопывает повтор одного ключа. Шторм — много разных событий по одному продукту за окно: консоль и notify заливает дежурного.

**Что сделать.** Порог: N новых/повторённых событий по `product_id` за M минут → один баннер/синтетика на продукт, freeze notify по этому продукту до спада. Показать счётчик «скрыто N» в консоли. Дефолты консервативные, конфиг в правиле или на продукте — один простой порог, не конструктор политик.

**Не делать.** Отдельный storm-сервис, очереди из §4.6 requirements как отдельный продукт, блокировка всего источника (уже есть `blocked` по статусу), ML, корреляция по топологии (это FM-3).

## FM-12 — PROBLEM/OK в правилах (закрытие аварии)

| | |
|---|---|
| **Ключ** | `FM-12` |
| **Статус** | `ready` |
| **Приоритет** | `Средний` |
| **Модули** | `backend/fm-module` (`RuleGraphTraverser`), canvas UI уже знает тип |
| **Откуда** | recovery в adapter pull (`status=ok`); блок `problem_resolution` в UI без runtime |

**Зачем (FM).** Авария должна гаснуть, когда источник прислал OK с тем же `externalId`. Иначе консоль копит PROBLEM, здоровье не восстанавливается без ручного close.

**Что сделать.** Исполнять `problem_resolution` в canvas: событие `ok`/`resolved` закрывает активный PROBLEM с совпадающим ключом (source + externalId / CI). Согласовать с уже существующим close и пересчётом health.

**Не делать.** Новый ingest, новые типы источников, RCA, combo, отдельный workflow «проблема ITIL».

## Как добавлять пункты

1. Заголовок + ключ `FM-<n>` (следующий свободный номер). Если есть тикет Jira — указать `WISLA-<n>` отдельно, не подменять им `FM-<n>`.
2. Статус, приоритет (Критический / Высокий / Средний / Низкий), модули, зависимость от активного change.
3. Почему отложено / критерий «можно брать».
4. Не тащить в текущий `/build-feature`, пока пользователь явно не скажет взять пункт из беклога.
