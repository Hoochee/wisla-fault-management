# Спецификация страниц — WISLA Fault Management

**Источник:** `docs/requirements.md`, `output.md`, [Monq Docs 9.1](https://docs.monq.ru/docs/guide/main-menu)  
**Визуальный стиль:** Monq — тёмная профессиональная тема, консоль оператора NOC, тепловые карты, severity-цвета, карты фильтров, конструктор запросов.

**Обозначения MVP:** страницы, обязательные для демо-сценария, помечены **MVP**.

## Детализация ключевых экранов

### Общий layout (Monq main-menu)

- **Sidebar слева:** логотип → контекст группы/тенанта → избранное → разделы → свернуть/развернуть.
- **Шапка:** хлебные крошки, глобальный поиск (post-MVP), профиль, выход.
- **In-app push (MVP+):** глобальный polling `GET /api/v1/notifications/push?since=` (интервал как у консоли, по умолчанию 60 с); новые записи — **toast** (заголовок события, текст из шаблона push-блока); клик по toast → `/console/:eventId`.
- **Тёмная тема:** фон `#1a1d23`–`#252830`, акценты severity, моноширинный шрифт для ID/времени.
- Персональные настройки (состав колонок, состояние sidebar) сохраняются в профиле пользователя.

### Dashboard (`/`)

**Макет (Monq «Оперативный центр» — упрощённо):**
- Верхняя панель: логотип WISLA FM, контекст группы, профиль.
- **Оперативные показатели:** кликабельные счётчики Critical / Major / Minor / Warning → `/console` с фильтром (1 клик).
- Виджет **«Карты событий»** / быстрый доступ: системные «Активные», «Закрытые» + пользовательские (2-й клик → консоль с картой).
- Превью тепловой карты «Здоровье продуктов» → `/health` (3-й клик до детализации продукта — через `/health/:id`).

### Консоль событий (`/console`)

**Структура экрана (Monq «События и логи» + «Сигналы»):**

```
┌─────────────┬──────────────────────────────────────────┐
│ Карты       │ [Конструктор запросов] [Датапикер] [⟳]   │
│ событий     ├──────────────────────────────────────────┤
│             │ Гистограмма событий по времени           │
│ • Активные  ├──────────────────────────────────────────┤
│ • Закрытые  │ Таблица / Список  [⚙ колонки] [+ карта]  │
│ • + своя    │                                          │
│             ├──────────────────────────────────────────┤
│             │ ▼ Карточка выбранного события (панель)   │
└─────────────┴──────────────────────────────────────────┘
```

**Колонки таблицы (MVP):** статус, критичность (цветная метка), заголовок, КЕ/FQDN, система, источник, created_at, assigned_to, repeat_count, **последний повтор** (`last_repeat_at` — дата/время последнего повтора; отображается при `repeat_count > 1`, иначе «—»).

**Поведение:**
- Переключатель **таблица / список**.
- **Сортировка колонок:** клик по заголовку → `GET /api/v1/events?sort={field},{asc|desc}`; поля: status, severity, title, nodeFqdn, systemName, createdAt, repeatCount, lastRepeatAt; по умолчанию `createdAt,desc`.
- Настройка колонок (шестерёнка): показать/скрыть, порядок, ширина — сохраняется в карте.
- Клик по строке → нижняя панель карточки; двойной клик / СКМ → `/console/:eventId` в новой вкладке.
- **Быстрый фильтр:** клик по значению ячейки → добавить/исключить из запроса.
- Контекстное меню: принять в работу, закрыть, комментарий, фильтр по объекту.
- Автообновление: 5 с – 5 мин (по умолчанию 1 мин), ручное ⟳.
- Подгрузка пакетами по 500 записей.

**Конструктор запросов (no-code):**
- Кнопка `+` → блок «поле — оператор — значение».
- Операторы: Равно, Не равно, Содержит, Больше, Меньше, Пустой.
- AND / OR, группы скобками.
- Сохранение запроса как именованного блока в строке поиска.

**Карты событий:**
- Левая колонка — список карт; `+` создать (название, запрос, колонки, личная/общая).
- Несохранённые изменения — цветовая индикация у названия карты.
- «Сохранить как» / «Сбросить изменения».

### Карточка события (`/console/:eventId`)

**Нижняя панель (быстрый просмотр) и полноэкранная карточка:**

**Вкладки:**
1. **Атрибуты** — таблица key/type/value + режим JSON; типы: string, number, boolean, date, UUID.
2. **Журнал действий** — хронология (взятие в работу, комментарии, смена статуса, корреляция).
3. **Связи** — корневая причина, дочерние, ручная корреляция.
4. **История** — изменения атрибутов (post-MVP).

**Панель действий:** Принять в работу | Закрыть | Комментарий | Подтвердить | ⋮ (копировать ID, открыть в новой вкладке).

**Сохранение на лету** для статуса, критичности, назначенного, тегов (как в Monq).

### Здоровье продуктов (`/health`)

**Визуал:** тепловая карта (grid или иерархия продуктов). Цвет ячейки = серверный `healthPercent` из `GET /api/v1/health/products` (не клиентский синтез и не только `maxSeverity`); интенсивность = `damagePercent`. SPA не строит выдуманные компоненты CPU/HDD и не генерирует synthetic timeline.

**Интеракция:** hover — tooltip (продукт, `healthPercent`, `damagePercent`, счётчики); click — `/health/:productId`.

> **Дельта product-health-graph:** список отдаёт additive `healthPercent`, `damagePercent`, `components[]`; поля `maxSeverity`, `activeEventCount`, `ciIds` сохраняются. CRUD продуктов без изменений (вариант B — `ciIds`).

> **Дельта health-product-crud:** CRUD продуктов на панели здоровья; привязка КЕ со стороны продукта (вариант B — поле `ciIds` в create/patch заменяет все строки `product_ci`). Write — **только Администратор** (`POST/PATCH/DELETE /api/v1/admin/products`); чтение тепловой карты — `GET /api/v1/health/products`.

**Toolbar (только Администратор):**
- Кнопка **«+ Продукт»** → модальная форма создания.

**Ячейка тепловой карты:**
- Дежурный / Специалист: click → `/health/:productId` (без действий редактирования).
- **Администратор:** иконка или контекстное меню на ячейке — **Редактировать**, **Удалить**; click по ячейке (не по иконке) — drill-down как для остальных ролей.

**Модальная форма продукта (create / edit, только Администратор):**
- **Название** (`name`) — обязательно.
- **Код** (`code`) — обязательно; уникальный; при дубликате API **409**.
- **Тенант** (`tenant`), **Площадка** (`site`) — обязательно.
- **Теги** (`tags`) — необязательно; в UI ввод через запятую, в API массив строк.
- **КЕ** (`ciIds`) — необязательно; multiselect из `GET /api/v1/admin/configuration-items` (поиск по FQDN); при create/patch с `ciIds` — полная замена связей M:N для продукта.
- **Не в форме (read-only):** `healthPercent`, `damagePercent`, `maxSeverity`, `activeEventCount` — с серверного снимка; отображаются на ячейке и карточке после сохранения.
- **Создать** → `POST /api/v1/admin/products` с `{ name, code, tenant, site, tags?, ciIds? }` → **201**; закрытие модалки, reload тепловой карты (`GET /api/v1/health/products`).
- **Сохранить** (edit) → `PATCH /api/v1/admin/products/{id}` с любым подмножеством полей; omit `ciIds` на patch → связи КЕ не меняются.
- Не-администратор: кнопки и модалка скрыты; API write → **403**.

**Удаление продукта (только Администратор):**
- **Удалить** → модальное подтверждение → `DELETE /api/v1/admin/products/{id}`.
- При **409** (есть связанные КЕ) — диалог «Сначала отвяжите КЕ»; кнопка **Открыть состав** → `/health/:productId`; продукт не удаляется.
- При **204** — reload тепловой карты; ячейка пропадает.

### Карточка продукта (`/health/:productId`)

> **Дельта product-health-graph:** карточка рисует только серверные данные (`GET /api/v1/health/products/{id}` и `.../history`). Sankey — `sankey.nodes` / `sankey.links[{from,to,damage}]` через **d3-sankey** (узкий Angular wrapper). Heatmap истории — бакеты `minHealth` / `maxHealth` / `worstSeverity` (default `bucketMinutes=15`). `health-profile.util.ts` — только цвета/labels.

> **Дельта health-product-crud:** блок **«Состав продукта»** — список связанных КЕ, добавление и отвязка через `PATCH` с `ciIds` (полная замена списка). Новые КЕ без слота попадают в `COMMON`.

**Шапка:** название, `code`, тенант, площадка, теги; badge `maxSeverity`; `healthPercent` / `damagePercent`; счётчик `activeEventCount`; min/max за сегодня; ссылка **В консоль** с предфильтром по продукту (все роли с R).

**Компоненты и урон:** список слотов из snapshot (`code`, `name`, `healthPercent`, `damagePercent`); не выдумывать CPU/HDD на клиенте.

**Sankey:** диаграмма урона продукт ← компоненты ← КЕ/сигналы; ширина ребра = `damage` с сервера.

**Heatmap истории:** `GET /api/v1/health/products/{id}/history?from&to&bucketMinutes=` (default 15 мин); ячейка — худший статус в бакете (`worstSeverity`) и диапазон `minHealth`–`maxHealth`.

**Редактор весов (только Администратор):** кнопка **«Веса компонентов»** на карточке открывает модалку с редактором слота (вес, `influenceType` `weighted` / `critical`, порог, состав КЕ слота). **Сохранить** в редакторе → `PATCH /api/v1/admin/products/{id}` с `{ "components": [{ code, name, weight, influenceType, criticalThreshold, ciIds }] }`. Отмена и клик по overlay закрывают модалку без PATCH. Успешный PATCH закрывает модалку и перезагружает карточку. Ошибка PATCH оставляет модалку открытой. Пока модалка закрыта, панель редактора на карточке не показывается. Omit `components` на других PATCH не трогает слоты. Все веса 0 → API **400**. Одна КЕ в двух слотах одного продукта → **400**. Дежурный / Специалист не видят кнопку и редактор; колонка **«Вес»** в таблице компонентов остаётся read-only.

**Блок «Состав продукта»:**
- **Все роли (R):** таблица связанных КЕ — FQDN, тип (`ciType`), система, подсистема.
- **Только Администратор:**
  - **«+ Добавить КЕ»** → picker/modal: список из `GET /api/v1/admin/configuration-items`, поиск по FQDN, multiselect; уже связанные КЕ отмечены; подтверждение добавляет id в локальный список и вызывает `PATCH /api/v1/admin/products/{id}` с `{ "ciIds": [uuid, …] }` (полный список после изменения).
  - **Отвязать** в строке → удаление id из списка → `PATCH` с обновлённым `ciIds` (пустой массив снимает все связи).
  - **Редактировать продукт** — та же модалка атрибутов, что на `/health` (без обязательного изменения `ciIds`).
- После успешного patch — reload карточки (`GET /api/v1/health/products/{id}`); тепловая карта на `/health` обновляется при следующем polling/reload.

**Активные события:** список/таблица событий по связанным КЕ; ссылка в `/console` с предфильтром.

**Удаление с карточки (только Администратор):** действие **Удалить продукт** — та же логика 409/204, что на `/health`; при 409 подсказка открыть блок «Состав продукта» и отвязать КЕ.

### Источники (`/sources`)

> **Дельта demo-preparing:** полный цикл настройки источника и демо с zabbix-simulator через UI (без DevTools / docker override).

**Экран списка (Monq «Потоки данных» + «Сборщики»):**
- **Карточка runtime adapter** (сверху): status сервиса `:8081`, version, buffered, доступность fm-module (`GET /api/v1/adapters/runtime`).
- Таблица: название, тип (Push REST / Pull), **статус конфигурации** (active / inactive), **колонка «Адаптер»** (running / idle / stopped / degraded / unreachable), last_success_at, adapter_version, API-ключ (маскированный, напр. `zk-****-…`).
- Рубрикатор: **Все / Запущен / Остановлен / Push** (фильтр по `adapterRuntimeStatus`, `status` и типу).
- Polling страницы: 30 с (обновление runtime + списка источников).
- Кнопки: **+ Создать**, **+ Мастер настройки** (post-MVP — шаблоны Zabbix/vCenter).
- **Переключатель active/inactive** в строке таблицы: `PATCH /api/v1/sources/{id}` с `{ "status": "active" | "inactive" }`; после успеха fm-module синхронизирует конфиг на adapter; toast с результатом; disabled при отсутствии прав.
- **Удалить** (иконка или контекстное меню строки): модальное подтверждение → `DELETE /api/v1/sources/{id}`. При **409** (есть связанные события) — вторичный диалог: «Невозможно удалить. Деактивировать источник?» → PATCH `{ "status": "inactive" }`; при успехе строка остаётся в реестре со статусом «Остановлен».
- Вкладка **Журнал запусков** для Pull (post-MVP).

**Создание (`/sources/new`):**
- Форма: **Название**, **Тип** (Push REST / Pull ETL / …), **Протокол**, **Endpoint** (URL внешней системы-источника; для Zabbix — адрес инстанса, не webhook FM).
- **Создать** → `POST /api/v1/sources` (по умолчанию `status=inactive`).
- После **201** — **модальное окно credentials** (блокирует навигацию до явного «Закрыть» / «Перейти к карточке»):
  - **Webhook URL** — публичный URL adapter (`EventSourceDetail.webhookUrl`, вид `{ADAPTER_PUBLIC_URL}/webhook/{pathKey}`).
  - **API-ключ** — полный plaintext (единственный показ; в последующих GET только маска).
  - Кнопки **Копировать** у каждого поля; предупреждение «Сохраните ключ — повторно он не отображается».
  - UI сохраняет пару `{ sourceId → ingestApiKey }` в **sessionStorage** текущей вкладки (для probe, bind-simulator, regenerate в этой сессии).
- Закрытие модалки → переход на `/sources/{id}`.

**Карточка источника (`/sources/:id`):**

**Шапка:** название, badge статуса (active/inactive), тип; действия: **Запустить / Остановить** (toggle, как в списке), **Тест подключения**, **Удалить** (та же логика 409 → деактивация), **Редактировать**.

**Блоки (режим просмотра):**
- **Основная информация:** ID, протокол, endpoint, версия адаптера, last_success_at, runtime адаптера (из `GET /api/v1/adapters/runtime` по sourceId).
- **Получение данных:** Webhook URL (readonly + **Копировать**), API-ключ (маскированный), кнопка **Сгенерировать новый ключ** → `PATCH { "regenerateApiKey": true }` → модалка credentials с новым plaintext-ключом (один раз) + обновление sessionStorage; fm-module sync adapter.
- **Пред-обработка** (парсер JSON), **Пост-обработка** → правила (ссылка на `/rules`).

**Форма редактирования** (кнопка «Редактировать» или inline-режим):
- Поля: **Название**, **Протокол**, **Endpoint**; **Сохранить** → `PATCH /api/v1/sources/{id}`; **Отмена** без изменений.
- После успешного patch — adapter config sync; toast.

**Тест подключения:**
- Кнопка **Тест подключения** → `POST /api/v1/sources/{id}/test` с телом `{ "ingestApiKey": "…" }` при необходимости.
- Ключ берётся из sessionStorage (после create/regenerate); если отсутствует — модальный prompt «Введите API-ключ источника» (для повторного теста в новой сессии).
- fm-module перед probe синхронизирует конфиг на adapter, затем adapter `POST /internal/probe`.
- Результат в UI: success/fail, `message`, `delivery` (forwarded / buffered / failed), `latencyMs`, `testedAt`; цветовая индикация (зелёный / красный / жёлтый при buffered).

**Демо-блок «Эмулятор Zabbix»** (виден на dev/demo-стенде; не заменяет настройку реального Zabbix Media Type):
- Заголовок с badge: **Не привязан** / **Привязан** / **Недоступен** (по `GET /api/v1/sources/{id}/simulator-status`).
- Polling статуса: 10–15 с (или после действий bind/tick/control).
- **Привязать эмулятор** — `POST /api/v1/sources/{id}/bind-simulator` с `{ "ingestApiKey" }` из sessionStorage (или prompt, если ключа нет); fm-module вызывает zabbix-simulator `POST /config` (webhook key + API key) и sync adapter; в ответе/статусе — `adapterWebhookUrl`, `sourceWebhookKey`, `simulatorEnabled`.
- **Статус привязки:** reachable, bound (совпадение webhook key), `adapterWebhookUrl`, `activeProblems`, подсказка `message`.
- **Отправить тестовое событие** — `POST /api/v1/sources/{id}/send-test-event` (прокси `POST /tick` на симулятор); disabled, пока `bound=false`; результат: `kind` (problem / recovery / skip / error), `delivered`, `httpStatus`; ссылка «Открыть консоль» с предфильтром по источнику.
- **Переключатель «Автотик»** — вкл/выкл периодической отправки на симуляторе (`POST /control` через fm-module); состояние отражается в `simulator-status.enabled`; рекомендуется выключать до завершения настройки credentials.
- Если симулятор недоступен (502) — блок в состоянии degraded с текстом ошибки, bind/tick disabled.

### Правила (`/rules`)

> **Дельта rules-enable-toggle:** вкл/выкл правила через `PATCH /api/v1/rules/{id}` с `{ "enabled": true | false }` (без отдельных activate/deactivate в UI).

**Экран (Monq «Бизнес-процессы» — упрощённо):**
- Список правил: название, тип (дедуп / problem-resolution / корреляция), статус вкл/выкл, **последний запуск** (`last_run_at` — обновляется при срабатывании action-блока).
- **Переключатель вкл/выкл** в строке таблицы: `PATCH /api/v1/rules/{id}` с `{ "enabled": true | false }`; при включении backend валидирует canvas (если есть nodes); при `400 canvas_validation` — toast с текстом ошибки, toggle возвращается в прежнее состояние; disabled при отсутствии прав.
- **+ Создать правило** → конструктор.

**Конструктор правила (`/rules/new`, `/rules/:id`):**

Визуальный **холст** (как Monq «Бизнес-процессы»). Сохранённый `canvas` (nodes/edges) **исполняется** backend при обработке каждого сырого события (включённые правила, по приоритету `created_at`). Пустой canvas → fallback по `rule_type`.

**Поддерживаемые блоки (MVP+):**

| Блок | Назначение | config (ключи) |
|------|------------|----------------|
| **trigger** | Старт цепочки | `triggerType: stream` (MVP+); `fm` — post-MVP |
| **condition** | Фильтр события | `field` (severity, title, status, nodeFqdn), `operator` (eq, ne, contains), `value`; несколько condition подряд = **AND** |
| **switch** | Ветвление | Исходящие ветки с condition; выполняется **первая** подходящая ветка (остальные пропускаются) |
| **dedup** | Слияние повторов | `key` (по умолчанию source_id + title + ci_id) → `repeat_count` в консоли |
| **threshold** | Порог в окне | `count`, `windowMin` → синтетическое fatal-событие при превышении |
| **correlation** | Связь root/child | `count`, `windowMin`, опционально `matchField` (title \| severity \| source) → первое событие в окне — **root**, последующие — **children** (`root_event_id` в карточке консоли) |
| **notify** | Исходящее оповещение | `channel` (`telegram` \| `email`); для `email` — обязательный `emailAddress`. MVP+ — **заглушка** (без реальной отправки); post-MVP — SMTP/Telegram |
| **push** | In-app toast оператору | `message` — шаблон с `{title}`, `{severity}`; runtime создаёт запись, UI получает через polling notifications API |
| **status** | Смена статуса | post-MVP: в палитре с предупреждением «не исполняется в runtime» |

**UI конструктора (`/rules/:id`):**
- **Шапка:** название, badge статуса (вкл/выкл), тип правила; действия: **Запустить / Остановить** (toggle `enabled`, как «Запустить БП» в Monq), **Сохранить**.
- Палитра блоков слева; drag-and-drop на холст; соединения edges между блоками.
- Панель свойств выбранного блока справа (редактирование `config`).
- Toggle **Запустить / Остановить** → `PATCH /api/v1/rules/{id}` с `{ "enabled": true | false }`; при ошибке валидации canvas — inline на холсте + toast; disabled при отсутствии прав.

**Валидация при Сохранить / Активировать:**
- Обязательно: ≥1 trigger с `triggerType=stream` и ≥1 action-блок (dedup \| threshold \| correlation \| **notify** \| **push**).
- Блок **notify**: обязателен `channel`; при `channel=email` — валидный `emailAddress` (ошибки API: `notify_missing_channel`, `notify_invalid_email`).
- Запрет: изолированные узлы без связей (orphan nodes).
- Ошибки — inline на холсте + ответ API `400` с текстом.
- Блоки **status** (и триггер **Событие FM**) — предупреждение post-MVP, не блокируют сохранение демо-схемы.
