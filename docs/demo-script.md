# Текст для демонстрации WISLA Fault Management

---

## Вступление (1–2 минуты)

Современные ИТ-системы — это не один мониторинг и не один сервер. Это сотни сервисов, сетевое оборудование, виртуализация, базы данных, облака и legacy-системы. Каждый из них ежедневно генерирует **тысячи сигналов**: алерты Zabbix, trap'ы SNMP, события vCenter, уведомления AlertManager, записи в логах приложений.

Проблема не в том, что данных много. Проблема в том, что они **разрознены**: разные форматы, разные интерфейсы, разная критичность. Дежурный инженер вынужден переключаться между пятью системами, вручную отсеивать шум и искать, что из этого действительно важно.

**WISLA Fault Management** — модуль, который собирает аварийные события из разных источников в **одном месте**, приводит их к единому виду и даёт оператору инструменты для работы: фильтрацию, сортировку, корреляцию и управление жизненным циклом инцидента.

---

## Задача, которую мы решаем

| Было | Стало с WISLA FM |
|------|------------------|
| Сигналы в Zabbix, логах, SNMP, OSS — отдельно | Единая консоль событий |
| Дубли одной и той же аварии | Дедупликация по правилам |
| Симптомы без связи с причиной | Корреляция root / child |
| Ручной разбор «что важнее» | Критичность, карты, сортировка по колонкам |
| Нет единого процесса обработки | Правила на визуальном холсте |

---

## Сценарий демонстрации

### 1. Источники событий

*«Начнём с того, откуда приходят данные.»*

В WISLA FM подключены **источники мониторинга** — Zabbix, SNMP, REST API и другие системы через адаптеры. Каждый источник регистрируется в реестре: протокол, endpoint, статус активности. События поступают в модуль по защищённому каналу и сразу попадают в единый поток обработки.

*Демо:* раздел **Источники** → показать список, карточку источника, отправку тестового события.

---

### 2. Первичные события

*«До обработки мы видим сырой поток — как он пришёл из системы.»*

Раздел **Первичные события** — это «входящая почта» мониторинга: всё, что принял адаптер, до дедупликации и правил. Здесь удобно проверить, что источник работает и данные доходят.

*Демо:* `/events/raw` → конструктор запросов, фильтр по критичности, гистограмма по времени.

---

### 3. Правила обработки

*«Дальше — интеллект системы. Не оператор решает, что делать с каждым сигналом, а настроенные правила.»*

На визуальном **холсте** собирается цепочка обработки:

- **Триггер** — событие из потока
- **Условие** — фильтр по критичности, заголовку, узлу
- **Дедупликация** — объединение повторов одной аварии
- **Порог** — «5 critical за 10 минут» → синтетическое событие
- **Корреляция** — связь симптомов с корневой причиной
- **Оповещение** — push в интерфейс, email, Telegram

Правила можно **включать и отключать** без удаления — удобно для тестов и согласования.

*Демо:* `/rules` → открыть правило с дедупликацией → показать canvas → включить/выключить.

---

### 4. Консоль событий — главный экран оператора

*«Это рабочее место дежурного. Здесь — уже обработанные события, готовые к действию.»*

**Консоль событий** объединяет всё, что прошло через правила:

- **Карты событий** — сохранённые наборы фильтров («Активные critical», «По продукту X»)
- **Конструктор запросов** — фильтрация по статусу, критичности, тексту
- **Гистограмма** — распределение событий во времени
- **Таблица** с сортировкой по колонкам: статус, критичность, заголовок, узел, система, **число повторов**, **последний повтор**, дата создания
- **Карточка события** — полные атрибуты, журнал действий, связи root/child, интеграция с ITSM

Оператор за **два–три клика** находит нужное: отфильтровал → отсортировал по последнему повтору → открыл карточку → взял в работу или закрыл.

*Демо:* `/console` → выбрать карту → клик по заголовку колонки «Последний повтор» → открыть событие с `repeat_count > 1` → показать связанные child-события.

---

### 5. Дашборд и здоровье продуктов

*«Для руководителя и дежурной смены — сводка, а не тысяча строк.»*

На **дашборде** — виджеты по критичности, быстрый переход в консоль с предустановленным фильтром. **Здоровье продуктов** — тепловая карта: цвет ячейки отражает максимальную критичность активных событий по продукту или системе.

*Демо:* `/` → клик по виджету → переход в консоль с фильтром.

---

### 6. Оповещения в реальном времени

*«Оператор не обязан постоянно смотреть в таблицу.»*

При срабатывании правил с блоком **push** в интерфейсе появляются **toast-уведомления** с заголовком события. Клик по уведомлению открывает карточку — можно сразу реагировать.

*Демо:* симулятор → несколько одинаковых событий → дедуп → toast → переход в карточку.

## Итоговый месседж

WISLA Fault Management — это **единая точка входа** для аварийных сигналов мониторинга:

1. **Собрать** — адаптеры принимают данные из Zabbix, SNMP, REST и других систем
2. **Обработать** — нормализация, дедупликация, корреляция, пороги — на настраиваемых правилах
3. **Показать** — консоль оператора с фильтрами, картами, сортировкой и карточками событий
4. **Оповестить** — push, email, Telegram, интеграция с ITSM

Вместо хаоса из разрозненных логов и алертов — **упорядоченный поток**, с которым дежурная смена может работать системно.

## Планы развития *(пометка для аудитории)*

> **В roadmap:**
> - **Модуль CMDB** — единый реестр конфигурационных единиц (узлы, системы, сервисы). Упростит привязку источников к инфраструктуре, обогащение событий атрибутами КЕ и навигацию «от события к объекту» без ручного ввода.
> - **Расширенная обработка логов** — приём и разбор прикладных логов (не только классические алерты мониторинга), поиск по тексту, связь log-событий с метриками и авариями в одной консоли.

Сегодня мы показываем **ядро FM**: приём сигналов, правила, консоль и жизненный цикл событий. CMDB и log-processing — следующий этап, который сделает платформу ещё ближе к полноценному центру наблюдаемости (observability) для крупной ИТ-инфраструктуры.

## Короткая версия (elevator pitch, ~30 секунд)

Современные ИТ-системы генерируют огромный поток логов и сигналов — Zabbix, SNMP, облака, приложения. WISLA Fault Management собирает их в одном модуле, нормализует, убирает дубли, связывает симптомы с причиной и показывает оператору удобную консоль с фильтрами и сортировкой. В планах — модуль CMDB для удобного управления источниками и расширенная обработка логов.
